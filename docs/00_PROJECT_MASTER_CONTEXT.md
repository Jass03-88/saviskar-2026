**Live deployment**: Vercel (`saviskar-2026.vercel.app`)

## 4. Business Rules

### 4.1 Participant Identity

- Every participant gets a **permanent participant ID** (format: `SVK26-XXXXXXXX`).
- Generated by the database function `register_participant_events` on first registration.
- The participant record **must NOT be deleted** when one event registration is deleted.
- The participant ID is reusable across multiple event registrations.

### 4.2 Registration Model

- **Free events**: Registration → confirmation email with QR → done.
- **Paid events**: Registration → confirmation email (payment pending) → Razorpay checkout → server-side verification → status = `paid` → receipt PDF → receipt email.

### 4.3 Two-Email System (Paid Events)

1. **Email 1 — Registration Confirmation**: Sent immediately after registration. Contains QR code. For paid events: shows "Payment: Pending".
2. **Email 2 — Payment Confirmation**: Sent ONLY after verified payment. Contains PDF receipt attachment. Subject includes "Receipt".

These two emails are **intentionally separate** and must never be merged.

### 4.4 QR Code Security

- QR encodes ONLY the permanent `participant_id` (e.g., `SVK26-ABC12345`).
- No payment IDs, payment status, secrets, or PII inside the QR.

## 5. Payment Architecture

### 5.1 Gateway Abstraction

The payment system is **intentionally gateway-agnostic**.

| File | Purpose |
|---|---|
| `lib/payments/types.ts` | `PaymentGateway` interface (createOrder, verifyPayment, getCheckoutConfig, validateWebhook) |
| `lib/payments/index.ts` | Gateway factory — reads `PAYMENT_GATEWAY` env var, defaults to `razorpay` |
| `lib/payments/razorpay.ts` | `RazorpayGateway` class (the only current implementation) |
| `lib/payments/post-payment.ts` | `ensurePaymentConfirmationSent()` — idempotent receipt PDF + email |

### 5.2 Payment Flow

```
Registration → payment_orders row (status=pending) → /api/payments/create (gateway order) →
Frontend Razorpay overlay → /api/payments/verify (HMAC signature check) →
payment_orders.status=paid → participant_events.payment_status=paid →
payments row → ensurePaymentConfirmationSent() → PDF receipt → receipt email
```

### 5.3 Payment States

| Status | Meaning |
|---|---|
| `paid` | Successfully verified payment |
| `pending` | Awaiting payment |
| `not_required` | Free event |
| `failed` | Payment attempt failed |

### 5.4 Payment Verification

Payment is **NEVER** marked `paid` by the frontend alone. Two server-side paths:

1. **`/api/payments/verify`** — Called after Razorpay checkout overlay completes.
2. **`/api/payments/webhook`** — Called by Razorpay server-to-server.

Both call `ensurePaymentConfirmationSent()` which uses an **atomic claim mechanism** on `payment_orders` to prevent duplicate receipt emails.

### 5.5 Receipt Idempotency

`payment_orders` has two columns for this:
- `receipt_email_claim_id` — UUID set atomically by the first process to claim.
- `receipt_email_sent_at` — Timestamp set after successful email delivery.

If email fails, the claim is released (set to `null`) so it can be retried.

## 7. Admin Roles

| Role | Privileges |
|---|---|
| **Master Admin** | Full access — event management, admin management, archive, permanent deletion, audit logs. Requires TOTP MFA (AAL2). |
| **Normal Admin** | Registration viewing and permitted check-in functionality. Cannot manage events, manage admins, archive, permanently delete, or view audit logs. |

**Server-side enforcement**: All admin API routes use `requireAdmin()` or `requireMasterAdmin()` from `lib/supabase/server.ts`. These check Supabase Auth + `admins` table + MFA level.

## 8. Database Model

```
participants (permanent identity)
  ├── participant_events (event-specific registration)
  │     ├── participant_event_members (team members)
  │     └── payment_order_items → payment_orders → payments
  └── payments (payment records)

admins (admin access control)
admin_audit_logs (audit trail)
events (event catalog)
```

### Key Relationships

- `participants.id` (UUID) ← `participant_events.participant_id` (FK)
- `events.id` ← `participant_events.event_id` (FK, ON DELETE RESTRICT)
- `payment_orders.payer_participant_id` → `participants.id` (ON DELETE SET NULL)
- `payment_order_items` links `payment_orders` to `participant_events`
- `admins.user_id` → `auth.users.id` (ON DELETE CASCADE)

### Archive vs Delete

- **Archive**: Sets `participant_events.is_archived = true`. Non-destructive. Reversible by Master Admin.
- **Permanent Delete**: Calls `delete_registration_permanently()` RPC function. Atomic within a single transaction. Audit log written in same transaction. Cleans up orphaned payment orders. **Preserves** the participant record.

## 9. Security Model

| Boundary | Enforcement |
|---|---|
| Admin API routes | Server-side `requireAdmin()` / `requireMasterAdmin()` |
| Permanent deletion | Server-side Master Admin check + database-level `SECURITY DEFINER` function |
| Payment verification | HMAC-SHA256 signature verification, server-side only |
| Payment secrets | `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` — server-only, never exposed to client |
| Receipt data | Generated from database-backed data, not client-supplied amounts |
| QR content | Participant ID only — no secrets or PII |
| Audit logs | RLS policy: only master admins can SELECT |
| Rate limiting | In-memory rate limiter on registration API (8 req/min per IP) |

## 10. Known Historical Issues

| Issue | Resolution |
|---|---|
| ₹ symbol in PDF receipt | pdf-lib's Helvetica/WinAnsi cannot encode ₹. **Current fix**: uses `INR` text. Do NOT reintroduce ₹ without embedding a Unicode-capable font. |
| Receipt PDF footer overlap | Fixed by calculating footer position from cursor position. |
| Empty base migration | Original `remote_schema` migration was empty. Repaired with full schema dump. Migration chain now initializes correctly. |
| Self-call deadlock in dev | Registration email is called directly via Resend SDK, not via HTTP self-fetch, to avoid Next.js dev/serverless deadlocks. |

## 11. Things That Must NOT Be Changed Casually

1. Payment gateway abstraction (`lib/payments/` interface boundary)
2. Participant ID generation and permanence
3. QR content (participant ID only)
4. Receipt email idempotency (`receipt_email_sent_at`, `receipt_email_claim_id`)
5. Two-email system (registration vs payment confirmation)
6. `is_archived` field (NOT `registration_status`) for archival
7. Admin role separation (server-side enforcement)
8. Atomic audit logging (same transaction as deletion)
9. Existing migrations (do not recreate, reorder, or delete)
10. Production database (do not reset)
